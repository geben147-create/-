05

고칠 것 아홉 가지

앞의 계획에서 실제로 사고가 나거나 시간을 버리게 되는 지점만 골랐습니다.

🔴🔴🔴C1

400GB를 옮기기 전에, 먼저 지워야 합니다

구글드라이브 이전이 1순위가 아닙니다. 캐시부터 비우면 통상 100~200GB가 옮길 필요 없이 사라집니다. 특히 WSL·Docker의 .vhdx는 안에서 파일을 지워도 파일 크기가 안 줄어듭니다 — 별도로 축소해야 합니다.

원안 순서D: 정리 → 구글드라이브 업로드 → 나중에 캐시 정리
바꾼 순서캐시 삭제 → vhdx 축소 → 남은 용량 재측정 → 그래도 부족하면 그때 업로드
# 조회만 (아무것도 안 지움)
.\02_YH_DISK_RECLAIM.ps1
# 실제 삭제
.\02_YH_DISK_RECLAIM.ps1 -Apply
🔴🔴🔴C2

구글 드라이브 데스크톱(스트리밍)은 쓰지 마세요

모델 가중치와 ComfyUI 용도에 최악입니다. 로컬 캐시가 C:를 다시 채워서 용량을 비운 의미가 사라지고, 랜덤 읽기가 느려 LTX 시작할 때마다 기다리게 됩니다. rclone으로 진짜 업로드하고 해시로 검증하세요.

보내면 안 되는 것활성 git 저장소 · ComfyUI/LTX 모델 · Obsidian Vault 원본 · Docker 볼륨
보내도 되는 것archive · backup · 완료된 outputs · 참고자료 · 다운받은 영상 원본
# 복사 → 검증 → 검증 통과해야만 원본 삭제
.\04_YH_GDRIVE_ARCHIVE.ps1 -Source "D:\AI_DATA\archive" -Dest "YH_ARCHIVE/archive"
.\04_YH_GDRIVE_ARCHIVE.ps1 -Source ... -Dest ... -Verify
.\04_YH_GDRIVE_ARCHIVE.ps1 -Source ... -Dest ... -DeleteSourceAfterVerify
# rclone sync 는 절대 쓰지 마세요 — 대상 파일을 지웁니다. copy 만.
🔴🔴🔴C3

Tailscale은 이사용이 아니라 상시 운영용입니다

"Tailscale 쓰면 옮기기 더 쉬운가?" — 대량 이전에는 오히려 느립니다. WireGuard 암복호화가 끼고, 직결에 실패하면 DERP 릴레이를 타면서 속도가 크게 떨어집니다. 같은 공유기에 물린 두 PC 사이라면 그냥 LAN이 빠릅니다.

400GB 일괄 이전Tailscale ✗ → 기가비트 LAN + robocopy / SMB
평상시 원격 조종Tailscale ✓ → 포트포워딩 없이 SSH·RDP 안전 연결
robocopy "D:\AI_DATA\archive" "\\YH-STORE\d$\AI_DATA\archive" /E /Z /MT:16 /R:2 /W:5
🔴🔴🔴C4

ffmpeg와 hyperframe은 "같이 쓰는" 대상이 아닙니다

hyperframe은 HTTP/2 라이브러리(h2·httpx의 의존성)로 수십 KB짜리 pip 패키지입니다. ffmpeg도 100MB 남짓한 단일 실행파일이고요. 네트워크로 공유할 크기도, 종류도 아닙니다. 그냥 각 PC에 설치하면 끝입니다.

하려던 것400만원 PC의 ffmpeg·파이썬 패키지를 다른 PC에서 네트워크로 참조
해야 할 것pip freeze > requirements.txt 로 재현 · winget install Gyan.FFmpeg 로 각자 설치

진짜로 다른 PC의 성능이 필요한 거라면 파일 공유가 아니라 SSH 원격 실행이 답입니다. 공유할 가치가 있는 건 모델 가중치와 미디어 파일뿐이고, 그마저도 자주 쓰는 모델은 각 PC 로컬 NVMe에 복제해 둬야 합니다.

ssh YH-FINISH "ffmpeg -i D:\in.mp4 -c:v hevc_nvenc D:\out.mp4"
🔴🔴🔴C5

GTX 1650에 인코딩을 맡기기 전에 재보세요

GTX 1650은 리비전에 따라 NVENC 세대가 다르고, 일부 초기 TU117 모델은 NVENC 자체가 없습니다. 게다가 i9의 CPU 인코딩(libx264)이 1650 NVENC보다 화질·용량 효율이 좋은 경우가 흔합니다. "약한 PC에 인코딩"은 자동으로 옳은 배치가 아닙니다.

ffmpeg -hide_banner -encoders | findstr nvenc
# 아무것도 안 나오면 YH-FINISH 는 인코딩 담당이 될 수 없습니다.
🔴🔴🔴C6

Hermes Agent 명령어들은 확인이 안 됐습니다

hermes gateway install, Windows 네이티브 지원, hermes backup — 인용된 GitHub 링크로는 확인되지 않았습니다. 이 위에 4대 아키텍처 전체를 얹기 전에 실제 저장소와 문서에서 명령어가 존재하는지 먼저 확인하세요. 없으면 Docker 컨테이너로 돌리는 쪽이 안전합니다.

Windows 에디션에 따라 필요한 게 다릅니다. audit 결과를 보고 정하면 됩니다.

🔴🔴🔴C8

SSH·RDP 방화벽은 전체 개방이 아니라 Tailscale 대역만

원안의 "Windows Firewall SSH rule"은 범위가 없습니다. 22번 포트를 그냥 열면 공유기 설정에 따라 인터넷에 노출될 수 있습니다. Tailscale 대역으로 잠그면 Tailscale에 로그인한 내 기기에서만 접속됩니다.

New-NetFirewallRule -DisplayName "YH SSH (Tailscale only)" `
  -Direction Inbound -Protocol TCP -LocalPort 22 -Action Allow `
  -RemoteAddress "100.64.0.0/10"
🔴🔴🔴C9

관리자 계정은 authorized_keys가 무시됩니다

Windows OpenSSH의 함정입니다. 관리자 그룹 계정이면 ~/.ssh/authorized_keys를 아무리 잘 넣어도 키 인증이 안 됩니다. 여기서 반나절 날리는 사람이 많습니다.

# 관리자 계정은 이 경로에 넣어야 합니다
C:\ProgramData\ssh\administrators_authorized_keys
# 권한도 Administrators / SYSTEM 만 남기고 상속 제거해야 동작합니다
06

그대로 두는 게 맞는 것

원안에서 잘 잡힌 판단들입니다. 바꾸지 마세요.

✅✅✅유지

오늘 D: 삭제 · 포맷 · Ubuntu unregister 전부 금지

D: 볼륨 레이블이 "UBUNTU 24_0"인 것과 WSL 배포판이 별개라는 지적, 정확합니다. 화면만 보고 지우면 복구가 안 됩니다. 그리고 COPY → 검증 → 그다음 원본 정리 순서를 못 박은 것도 맞습니다. MOVE를 먼저 하면 동기화 사고 때 원본이 같이 날아갑니다.

✅✅✅유지

Obsidian Vault는 4070에 원본 하나로

Vault를 네트워크 드라이브에 올리거나 여러 PC가 동시 편집하면 인덱스와 그래프 링크가 꼬입니다. 원본은 4070, 나머지는 미러 — 이 구조가 맞습니다. 활성 프로젝트를 느린 PC로 안 보내는 판단도 마찬가지고요.

✅✅✅유지

읽기 전용 점검을 먼저, 그 숫자로 역할 확정

"i3와 i7 중 SSD 상태·용량·전력을 오늘 검사해보고 역할을 서로 바꿀 수 있다"는 대목이 이 계획에서 가장 좋은 부분입니다. 추측으로 배치하지 않겠다는 태도. Hermes 이전을 백업 → 신규 설치 → 검증 → 구 인스턴스 정지 순으로 잡은 것도 정확합니다.
