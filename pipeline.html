Production Pipeline

전체 파이프라인
— 이 홈페이지는 실제로 이렇게 만들어졌다

영상 하나를 배경에 까는 게 아니라, 섹션마다 다른 클립을 스크롤 위치에 물리는 구조다. 어느 단계에서 무엇이 결정되는지 먼저 잡아야 뒤에서 고생하지 않는다. 아래는 이 저장소의 랜딩 페이지를 만들면서 실제로 사용한 모델·프롬프트·크레딧·명령어 전부다.

02

고장 진단 — 왜 비행기가 화면 뒤로 숨는가

겪는 증상들을 영상 생성 탓 / 웹 적용 탓으로 갈랐다. 대부분은 둘 다인데, 고쳐야 할 지점은 하나다.

증상진짜 원인고칠 곳조치
피사체가 화면 밖으로 사라진다 (모바일에서 특히) object-fit:cover + 화면 비율 차이. 16:9 를 세로 화면에 깔면 가로의 68%가 잘려나간다. 양쪽 피사체를 중앙 세이프존 안에 두고 생성 → 03번, 웹에서는 object-position 조정 + 모바일용 세로 소스 별도
피사체가 프레임을 벗어난다 (PC에서도) 프롬프트의 fly through, passes by, flies past camera. 모델이 충실히 화면 밖으로 보낸다. 영상 생성 “피사체는 전 구간 프레임 안에 유지”를 명시. 카메라는 따라가는 무브만
글씨가 영상 뒤로 들어간다 부모에 transform·filter·opacity<1·backdrop-filter·will-change 가 걸리면 새 stacking context 가 생겨 자식의 z-index:9999 도 밖으로 못 나간다. 웹 적용 isolation:isolate 를 일부러 걸고 그 안에서 영상 0 / 스크림 1 / 텍스트 2 → 05번
고정 요소가 스크롤에 딸려 사라진다 position:fixed 가 transform 걸린 조상 안에 있으면 뷰포트가 아니라 그 조상 기준이 된다. GSAP 핀 쓸 때 가장 흔한 사고. 웹 적용 fixed 요소를 <body> 직속으로 빼거나 조상의 transform 제거
글씨가 밝은 장면에서만 안 보인다 스크림 없이 흰 글씨. 영상은 프레임마다 밝기가 변하므로 평균이 아니라 최악 프레임 기준으로 계산해야 한다. 웹 적용 스크림 알파를 수치로 계산 → 06번
글씨가 튀어서 촌스럽다 text-shadow 남발 + 순백 #FFFFFF + 영상 위 컬러 텍스트. 셋 다 저가 템플릿의 신호. 웹 적용 그림자 대신 그라디언트 스크림, 순백 대신 #F2F5F9, 영상 위 컬러 금지
중간에 장면이 갑자기 바뀐다(컷) 5초 클립인데 모델이 알아서 컷 편집을 넣음. 배경으로는 치명적. 영상 생성 “단일 연속 촬영, 컷 없음”을 프롬프트와 네거티브 양쪽에
스크럽이 뚝뚝 끊긴다 키프레임 간격이 넓어 currentTime 을 바꿔도 실제 프레임이 안 바뀐다. 초당 1~2회만 갱신. 인코딩 keyint=1 전 프레임 키프레임으로 재인코딩 → 04번
모바일에서 영상이 아예 안 나온다 muted·playsinline 누락. iOS 는 자동재생을 거부하고 검은 화면으로 둔다. 웹 적용 autoplay muted loop playsinline 4개 전부 + poster
같은 프롬프트인데 결과가 매번 다르다 text→video 는 구도까지 매번 새로 만든다. 재현성이 없다. 영상 생성 image→video 로 전환. 구도는 이미지에서 확정하고 영상 모델에는 모션만 시킨다
여러 섹션의 영상 톤이 제각각이다 샷마다 따로 생성하면 색·질감·조명이 안 맞는다. 양쪽 동일 팔레트를 모든 프롬프트에 HEX 로 못박고 마지막에 ffmpeg 그레이딩 통일
가장 자주 걸리는 함정 두 개.
① 영상 생성 단계에서 text→video 로 뽑고 있다 → image→video 로 바꾸면 “매번 다르게 나오는” 문제의 절반이 사라진다.
② 웹 적용 단계에서 stacking context 를 모르고 z-index 만 올리고 있다 → isolation:isolate 한 줄이면 끝난다.
03

세이프존 — 잘려도 살아남는 구도를 숫자로

“모바일에서 피사체가 사라진다”는 감이 아니라 계산이다. object-fit:cover 는 화면을 채우려고 넘치는 쪽을 잘라낸다. 16:9(1.778) 영상을 세로 화면에 깔면 보이는 가로 비율은 화면비 ÷ 1.778 이다.

절대 세이프존 = 가로 중앙 26% × 세로 중앙 76%. 핵심 피사체와 텍스트는 반드시 여기 안.
권장 세이프존 = 가로 중앙 42% × 세로 중앙 84% (모바일 전용 세로 소스를 따로 뽑는 경우).
세로가 76%만 보인다는 건 상하 12%씩 잘린다는 뜻이다. 상단에 뭔가 넣지 말 것.
이 빌드가 세이프존을 지킨 방법: 모든 첫 프레임 프롬프트에 subject centered within the middle 26 percent of the frame 와 the left third, the right third are empty / in deep shadow 를 명시했다. 덕분에 좌우가 잘려도 피사체가 살고, 동시에 그 어두운 좌우 영역이 그대로 텍스트 자리가 된다. 히어로는 여기에 더해 9:16 세로 소스를 별도 생성했다 — 하나로 두 화면을 덮으려는 시도가 결국 실패의 원인이다.

STEP 2 — 첫 프레임으로 구도를 못박는다

영상 모델에게 구도까지 맡기지 않는다. 이미지로 구도를 확정하고 영상 모델은 움직임만 담당한다. 재현성이 여기서 생긴다. 그리고 여기서 미리 어둡게 뽑는 게 핵심이다 — 밝은 영상 위에 글씨를 얹으려면 검은 막을 두껍게 깔아야 하고, 그러면 애써 만든 영상이 안 보인다.

STEP 3 — image→video, 시작·끝 프레임을 같게

kling-v2-5-turbo 의 pro 모드는 imageTail(끝 프레임)을 받는다. 시작 프레임과 끝 프레임에 같은 이미지를 넣으면 루프가 자연스럽게 닫힌다 — 이음매를 없애는 가장 확실한 방법이고, 후처리로 crossfade 를 넣는 것보다 결과가 깨끗하다.

STEP 4 — 웹용 인코딩

Pollo 에서 받은 mp4 를 그대로 올리면 안 된다. 용도별로 인코딩이 다르다. 스크럽이 끊기는 문제의 원인이 대부분 여기다.

A · 루프 배경용 — 가장 많이 쓴다 
ffmpeg -i in.mp4 -an \
  -vf "scale=1920:-2,fps=30" \
  -c:v libx264 -crf 24 -preset slow -profile:v high -pix_fmt yuv420p \
  -movflags +faststart hero-1920.mp4          # faststart: 첫 바이트에서 바로 재생

# 모바일 세로용 (별도 생성한 9:16 소스)
ffmpeg -i in-vertical.mp4 -an -vf "scale=1080:-2,fps=30" \
  -c:v libx264 -crf 25 -preset slow -pix_fmt yuv420p \
  -movflags +faststart hero-1080v.mp4

# webm 추가 — 브라우저가 알아서 더 작은 쪽을 고른다
ffmpeg -i in.mp4 -an -vf "scale=1920:-2,fps=30" \
  -c:v libvpx-vp9 -crf 34 -b:v 0 -row-mt 1 hero-1920.webm
B · 스크럽용 — 전 프레임 키프레임 
# keyint=1 이 핵심. 모든 프레임을 키프레임으로 만들어
# currentTime 을 어디로 옮겨도 즉시 그 프레임이 나온다.
ffmpeg -i in.mp4 -an \
  -vf "scale=1600:-2,fps=24" \
  -c:v libx264 -x264opts keyint=1:min-keyint=1:no-scenecut \
  -crf 22 -preset slow -pix_fmt yuv420p \
  -movflags +faststart scrub.mp4

# 주의: 용량이 3~5배 커진다. 스크럽 섹션 하나에만 쓸 것.
C · 포스터 — 없으면 iOS 저전력 모드에서 검은 화면 
ffmpeg -i hero-1920.mp4 -vframes 1 -q:v 82 poster.webp

# 6개 클립 색이 제각각일 때 전체 톤 통일
ffmpeg -i in.mp4 -vf "eq=brightness=-0.04:contrast=1.06:saturation=0.88" \
  -c:v libx264 -crf 24 -preset slow graded.mp4

용량 예산 — 이 선을 넘으면 사이트가 무거워진다

항목상한넘겼을 때
히어로 루프 (데스크톱)2.5MB첫 화면이 늦게 뜬다
히어로 루프 (모바일)1.2MBLTE 에서 재생이 안 된다

STEP 5 — 웹 조립: 글씨가 뒤로 안 가는 구조

핵심은 isolation:isolate 한 줄이다. 이걸 걸면 stacking context 가 의도적으로 만들어지고, 그 안의 z-index 가 항상 그 안에서만 계산되어 바깥 요소와 싸우지 않는다.

assets/css/site.css — 레이어 순서를 여기서 못박는다 
.hero{
  position: relative;
  isolation: isolate;        /* ★ 여기서 stacking context 를 "의도적으로" 만든다 */
  min-height: 78vh;          /* 100vh 금지 — 모바일 주소창 + 노트북 세로 공간 */
  display: grid; align-items: end; overflow: hidden;
}
.hero__bg{
  position: absolute; inset: 0; width: 100%; height: 100%;
  object-fit: cover;
  object-position: 50% 45%;  /* 피사체 위치에 맞춰 조정 */
  z-index: 0; pointer-events: none;
}
.hero__scrim{
  position: absolute; inset: 0; z-index: 1;   /* 영상 위, 글씨 아래 */
  background:
    linear-gradient(to top,
      rgba(8,10,14,.88) 0%,  rgba(8,10,14,.72) 26%,
      rgba(8,10,14,.34) 55%, rgba(8,10,14,.08) 100%),
    linear-gradient(to right,
      rgba(8,10,14,.62) 0%,  rgba(8,10,14,.14) 48%, rgba(8,10,14,0) 74%);
  pointer-events: none;
}
.hero__copy{ position: relative; z-index: 2; }   /* ★ 항상 맨 위 */
절대 하지 말 것 — 이게 “글씨가 뒤로 가는” 진짜 원인이다.
· .hero 의 조상에 transform·filter·opacity:.99·will-change 를 걸지 말 것. 걸리는 순간 position:fixed 자식이 뷰포트가 아니라 그 조상 기준이 되고 핀이 깨진다.
· 텍스트에 mix-blend-mode: difference / screen 금지. 밝은 프레임에서 글자가 통째로 사라진다.
· 스크림을 <video> 의 filter: brightness() 로 대체하지 말 것. 영상 전체가 죽고 GPU 부담만 는다.
· z-index 를 9999 로 올리는 건 해결이 아니다. context 가 다르면 아무 소용 없다.

스크럽을 GSAP 핀이 아니라 position:sticky 로 건 이유

GSAP ScrollTrigger 의 pin:true 는 핀 래퍼에 transform 을 만든다. 그러면 위의 “절대 하지 말 것” 첫 줄에 스스로 걸려서, 같은 페이지의 position:fixed 내비게이션이 깨진다. sticky 는 transform 을 만들지 않으므로 두 개가 공존한다. 스크럽 계산은 getBoundingClientRect() 로 직접 한다.

assets/js/site.js — 스크럽 핵심부 
stage.style.position = 'sticky';   // transform 을 만들지 않는 핀
stage.style.top = '0';

function loop(){
  target = progress() * duration;
  current += (target - current) * 0.18;      // 관성 (GSAP 의 scrub:0.6 에 해당)

  if (!video.paused) video.pause();          // 재생 중이면 seek 가 무시된다
  video.currentTime = Math.max(0, Math.min(duration - 0.02, current));

  paint(progress());
  requestAnimationFrame(loop);
}
iOS Safari 에서 스크럽이 계속 끊긴다면 비디오 스크럽을 포기하고 이미지 시퀀스로 바꾼다. canvas 에 drawImage 로 프레임을 그리는 방식이라 기기 편차가 없다. 애플이 자기 제품 페이지에서 비디오가 아니라 이미지 시퀀스를 쓰는 이유가 이것이다. 전환 명령어는 build.sh 안에 주석으로 준비해 두었다.

STEP 6 — 텍스트 & 컬러: 계산된 수치

“안 보이거나 촌스럽거나”는 취향 문제가 아니라 대비비 계산 문제다. 영상은 프레임마다 밝기가 변하므로 최악 프레임(순백)을 기준으로 잡는다.

스크림 알파 — 실제 계산값

스크림 색 #080A0E 를 순백(#FFFFFF) 프레임 위에 알파 a 로 깔았을 때, 그 위 흰 글씨의 대비비. 이게 이 영상에서 나올 수 있는 최악의 값이다.

· 더 좋은 방법: 영상 자체를 어둡게 뽑으면 알파를 0.35까지 낮춰도 되고 영상도 산다 → 이 빌드가 택한 방법

이 환경에서 실행하지 못한 단계

STEP 4 (웹 인코딩) 은 로컬에서 실행해야 한다. 이 저장소를 만든 실행 환경은 조직 egress 정책이 videocdn.pollo.ai 를 차단한다 (403 CONNECT). 생성은 MCP 채널로 정상 수행됐지만 결과물 바이트를 컨테이너로 내려받을 수 없어 ffmpeg 인코딩·포스터 추출·용량 측정을 대신 수행하지 못했다. 정책을 우회하지 않고 그대로 남겨 둔다.

같은 이유로 생성된 프레임을 직접 열어보는 시각 검수(07번 체크리스트)를 수행하지 못했다. 프롬프트 차원의 세이프존·어두운 톤 강제는 전부 걸어 두었지만, 실제로 390px 폭에서 피사체가 살아 있는지와 가장 밝은 프레임에서 글자가 읽히는지는 브라우저에서 한 번 확인해야 한다. 어긋나는 샷이 있으면 해당 샷만 다시 생성하면 된다 (첫 프레임 재생성은 0크레딧).
