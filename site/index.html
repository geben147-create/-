알아야 할 개념 3가지

개념 1

스크럽 (Scrub)

스크롤 위치를 영상의 재생 시점(currentTime)에 직결하는 것. 스크롤을 멈추면 영상도 멈추고, 거꾸로 올리면 영상도 되감깁니다. 애플 제품 페이지 방식.

개념 2

핀 (Pin)

스크롤하는 동안 특정 섹션을 화면에 고정시키는 것. 핀 없이 스크럽만 걸면 영상이 화면 밖으로 밀려 올라가며 재생됩니다.

개념 3

루프 (Loop)

스크롤과 무관하게 무한 반복 재생. 히어로 배경에 씁니다. 첫 프레임과 끝 프레임이 같아야 이음매가 안 보입니다.

원칙을 하나만 고르라면 — 영상 안에 글자를 넣지 마세요.
AI 영상 모델은 한글을 제대로 못 씁니다. 설령 잘 나와도 반응형·검색엔진·번역·접근성이 전부 죽습니다. 글자는 무조건 HTML 레이어, 영상은 배경만.

어떤 방식으로 만들 것인가 — 3가지 선택지

추천 순서: 1차 완성은 전부 루프 비디오로. 화면이 다 맞춰진 뒤에 “이 섹션 하나만” 스크럽으로 승격시키세요.
방식난이도안정성용량언제 쓰나
루프 비디오
<video loop>		 낮음매우 높음1~3MB 히어로 배경, 섹션 배경. 90%는 이걸로 충분합니다. 먼저 이걸로 완성하고 나중에 스크럽을 얹으세요.
비디오 스크럽
currentTime 제어		 중간기기별 편차3~8MB 제품 회전, 카메라 이동 등 “스크롤로 조종하는” 느낌이 핵심일 때. iOS Safari에서 끊기기 쉬움.
이미지 시퀀스
canvas + WebP		 중간매우 높음4~12MB 스크럽을 반드시 매끄럽게 해야 할 때. 앞뒤 이동이 완벽. 애플이 실제로 쓰는 방식.

처음부터 스크럽으로 짜면 디자인을 고칠 때마다 영상을 다시 뽑아야 합니다.

02 / DIAGNOSIS

왜 비행기가
화면 뒤로 숨는가

증상을 영상 생성 탓 / 웹 적용 탓으로 갈랐습니다. 대부분은 둘 중 하나가 아니라 둘 다인데, 고쳐야 할 지점은 하나입니다.

증상별 원인표 — 왼쪽에서 자기 증상을 찾고, ‘고칠 곳’ 열만 보세요.
증상진짜 원인고칠 곳조치
비행기가 화면 밖으로 사라진다 (모바일에서 특히) object-fit:cover + 화면 비율 차이. 16:9 영상을 세로 화면에 깔면 가로의 68%가 잘려나갑니다. 양쪽 피사체를 중앙 세이프존 안에 두고 생성(→ 03), 웹에서는 object-position 조정 + 모바일용 세로 소스 별도 준비
피사체가 프레임을 벗어난다 (PC에서도) 프롬프트에 fly through, camera passes by 같은 지시어. 모델이 충실히 화면 밖으로 보냅니다. 영상 생성 “피사체는 전 구간 프레임 안에 유지”를 명시. 카메라는 피사체를 따라가는 무브만 지시
글씨가 영상 뒤로 들어간다 부모에 transform·filter·opacity<1·backdrop-filter·will-change가 걸리면 새 stacking context가 생겨 자식의 z-index:9999도 밖으로 못 나갑니다. 웹 적용 히어로에 isolation:isolate를 일부러 걸고 그 안에서 영상 0 / 스크림 1 / 텍스트 2로 정리 (→ 08)
고정해 둔 요소가 스크롤에 딸려 사라진다 position:fixed가 transform 걸린 조상 안에 있으면 뷰포트가 아니라 그 조상 기준이 됩니다. GSAP 핀 쓸 때 가장 흔한 사고. 웹 적용 fixed 요소를 <body> 직속으로 빼거나, 조상의 transform을 제거
글씨가 밝은 장면에서만 안 보인다 스크림 없이 글씨를 얹음. 영상은 프레임마다 밝기가 변하므로 평균이 아니라 최악 프레임 기준으로 계산해야 합니다. 웹 적용 스크림 알파를 수치로 계산해 적용 (→ 09)
글씨가 튀어서 촌스럽다 text-shadow 남발 + 순색 + 영상 위 컬러 텍스트. 셋 다 저가 템플릿의 신호입니다. 웹 적용 그림자 대신 그라디언트 스크림, 순색 대신 한 단계 낮춘 톤, 영상 위 컬러 금지 (→ 09)
중간에 장면이 갑자기 바뀐다(컷) 5초 클립인데 모델이 알아서 컷 편집을 넣음. 홈페이지 배경으로는 치명적. 영상 생성 “단일 연속 촬영, 컷 없음, 장면 전환 없음”을 프롬프트와 네거티브 양쪽에
스크럽이 뚝뚝 끊긴다 키프레임 간격이 넓어 currentTime을 바꿔도 실제 프레임이 안 바뀜. 초당 1~2회만 갱신됩니다. 인코딩 전 프레임 키프레임(all-intra)으로 재인코딩하거나 이미지 시퀀스로 전환 (→ 07)
모바일에서 영상이 아예 안 나온다 muted·playsinline 누락. iOS는 자동재생을 거부하고 검은 화면 또는 첫 프레임 정지 상태로 둡니다. 웹 적용 autoplay muted loop playsinline 4개 전부 + poster 지정
같은 프롬프트인데 결과가 매번 다르다 text→video는 구도까지 매번 새로 만듭니다. 재현성이 없습니다. 영상 생성 image→video로 전환. 구도는 이미지에서 확정하고 영상 모델에는 모션만 시킵니다 (→ 05)
여러 섹션의 영상 톤이 제각각이다 샷마다 따로 생성하면 색·질감·조명이 안 맞습니다. 양쪽 ref2video 모델로 레퍼런스 고정 + 마지막에 ffmpeg 그레이딩 통일 (→ 06, 07)
가장 자주 걸리는 함정 두 개만 기억하세요.
① 영상 생성 단계 — text→video로 뽑고 있다. → image→video로 바꾸면 “매번 다르게 나오는” 문제의 절반이 사라집니다.
② 웹 적용 단계 — stacking context를 모르고 z-index만 올리고 있다. → isolation:isolate 한 줄이면 끝납니다.

03 / SAFE ZONE

잘려도 살아남는 구도를
숫자로 정한다

“모바일에서 피사체가 사라진다”는 감이 아니라 계산입니다.

  1. 16:9 소스를 세로 화면에 깔면, 높이를 맞추느라 가로가 잘립니다.
  2. 보이는 가로 비율 = 화면비 ÷ 1.778. 아이폰 풀블리드는 26%.
  3. 그래서 절대 세이프존은 가로 중앙 26% × 세로 중앙 76%입니다.
  4. 피사체·텍스트·로고는 전부 이 안에. 밖은 모바일에서 소멸합니다.
object-fit:cover는 화면을 꽉 채우기 위해 넘치는 쪽을 잘라냅니다. 16:9(1.778) 소스 기준.
화면비율보이는 가로보이는 세로
울트라와이드 모니터21:9 (2.333)100%76%
일반 데스크톱 히어로16:9 (1.778)100%100%
노트북 / 창 좁힘4:3 (1.333)75%100%
태블릿 세로3:4 (0.750)42%100%
모바일 세로9:16 (0.563)32%100%
아이폰 풀블리드9:19.5 (0.462)26%100%
절대 세이프존 500 × 820
피사체 · 텍스트 · 로고 전부 여기

1920 × 1080 기준. 붉은 영역은 아이폰 풀블리드에서 잘려 사라집니다 — 가로 710px 밖, 세로 상하 각 130px. 권장 세이프존(가로 42% = 806px, 557~1363px)은 태블릿까지만 보장합니다.

되는 방법

이미지 단계에서 확정한다

첫 프레임을 만들 때 피사체를 중앙에 몰아넣고 좌우는 배경으로 채웁니다. 영상 모델은 구도를 유지할 뿐 교정하지 않습니다.

프롬프트에 여백을 명시하세요. “좌우 3분의 1은 비워 둔다”, “피사체는 중앙에 배치”는 실제로 먹힙니다.

정답

모바일 소스를 따로 뽑는다

크레딧이 두 배 들지만, 하나로 두 화면을 다 커버하려는 시도가 결국 “비행기가 사라지는” 원인입니다. 같은 첫 프레임을 세로로 리프레임해서 image→video를 한 번 더 돌리세요.

임시방편: 모바일에서 object-position을 피사체 쪽으로 밀면 급한 불은 끕니다. 근본 해결은 아닙니다.

04 – 07 / PRODUCTION

샷 설계 → 첫 프레임 → 영상 → 인코딩

여기서 30분 쓰면 크레딧 수만 원을 아낍니다. 섹션 하나 = 클립 하나가 기본 단위입니다.

STEP 1

샷 설계

카메라 무브는 샷당 하나. “천천히 전진하면서 위로 올라가고 동시에 회전”을 넣으면 모델이 셋 중 하나를 골라 과장하거나 셋 다 어설프게 섞습니다. 어색함의 최대 원인입니다.

STEP 2

첫 프레임 이미지

영상 모델에게 구도까지 맡기지 않습니다. 이미지로 구도를 못 박고, 영상 모델은 움직임만 담당하게 합니다. 재현성이 여기서 생깁니다.

STEP 3 · 4

영상 생성 · 인코딩

image→video로만 뽑습니다. 받은 mp4를 그대로 올리지 말고 용도별로 다시 인코딩하세요. 스크럽이 끊기는 원인의 대부분이 여기입니다.

07 / ENCODING

웹용 인코딩 — 여기를 건너뛰면 느려집니다

받은 mp4를 그대로 올리면 안 됩니다. 용도별로 인코딩이 다릅니다.

A · 루프 배경용 — 가장 많이 씁니다

ffmpegffmpeg -i in.mp4 -an \
  -vf "scale=1920:-2,fps=30" \
  -c:v libx264 -crf 24 -preset slow -profile:v high -pix_fmt yuv420p \
  -movflags +faststart hero-1920.mp4

# 모바일 세로용
ffmpeg -i in-vertical.mp4 -an -vf "scale=1080:-2,fps=30" \
  -c:v libx264 -crf 25 -preset slow -pix_fmt yuv420p \
  -movflags +faststart hero-1080v.mp4

# 용량 더 줄이려면 webm 추가 (브라우저가 알아서 고름)
ffmpeg -i in.mp4 -an -vf "scale=1920:-2,fps=30" \
  -c:v libvpx-vp9 -crf 34 -b:v 0 -row-mt 1 hero-1920.webm

B · 스크럽용 — 전 프레임 키프레임

ffmpeg# keyint=1 이 핵심. 모든 프레임을 키프레임으로 만들어
# currentTime 을 어디로 옮겨도 즉시 그 프레임이 나옵니다.
ffmpeg -i in.mp4 -an \
  -vf "scale=1600:-2,fps=24" \
  -c:v libx264 -x264opts keyint=1:min-keyint=1:no-scenecut \
  -crf 22 -preset slow -pix_fmt yuv420p \
  -movflags +faststart scrub.mp4

# 주의: 용량이 3~5배 커집니다. 스크럽 섹션 하나에만 쓰세요.

C · 이미지 시퀀스 — 스크럽을 확실히 하려면

ffmpegmkdir -p frames
ffmpeg -i in.mp4 -vf "fps=24,scale=1600:-2" -q:v 78 frames/%04d.webp

# 8초 × 24fps = 192장. 장당 60~90KB → 합계 약 12~17MB
# 프레임 수를 줄이려면 fps=16 (192 → 128장)

D · 모바일 크롭 · 포스터 · 톤 통일

ffmpeg# 16:9 를 9:16 으로 중앙 크롭 (임시방편 — 별도 생성이 정답)
ffmpeg -i in.mp4 -an -vf "crop=ih*9/16:ih,scale=1080:-2" \
  -c:v libx264 -crf 25 -preset slow -pix_fmt yuv420p \
  -movflags +faststart mobile.mp4

# poster 이미지 (첫 프레임) — 영상 로드 전 표시됨. 필수입니다.
ffmpeg -i hero-1920.mp4 -vframes 1 -q:v 82 poster.webp

# 전체 톤 통일 (6개 클립 색이 제각각일 때)
ffmpeg -i in.mp4 -vf "eq=brightness=-0.04:contrast=1.06:saturation=0.88" \
  -c:v libx264 -crf 24 -preset slow graded.mp4
용량 예산 — 이 선을 넘으면 사이트가 무거워집니다.
항목상한넘겼을 때
히어로 루프 (데스크톱)2.5MB첫 화면이 늦게 뜹니다
히어로 루프 (모바일)1.2MBLTE에서 재생이 안 됩니다
일반 섹션 루프1.5MB스크롤 중 버벅임
스크럽 클립6MB스크럽 시작이 느립니다
첫 화면 전체 (히어로+폰트+CSS)4MB이탈률 상승
히어로 외 섹션 영상은 preload="none" + IntersectionObserver로 화면에 들어올 때 로드하세요. 6개 영상을 동시에 받으면 첫 화면이 죽습니다.

08 / ASSEMBLY

글씨가 뒤로 안 가는 구조

아래 골격을 그대로 쓰면 stacking context 사고가 원천적으로 안 납니다. 핵심은 isolation:isolate 한 줄입니다.

html<section class="hero">
  <video class="hero__bg" autoplay muted loop playsinline
         preload="metadata" poster="/media/poster.webp">
    <source src="/media/hero-1080v.mp4" media="(max-width: 768px)" type="video/mp4">
    <source src="/media/hero-1920.webm" type="video/webm">
    <source src="/media/hero-1920.mp4"  type="video/mp4">
  </video>
  <div class="hero__scrim" aria-hidden="true"></div>
  <div class="hero__copy"> … </div>
</section>
css.hero{
  position: relative;
  isolation: isolate;   /* ★ stacking context 를 "의도적으로" 만든다.
                              이 한 줄 덕분에 아래 z-index 가 항상 이 안에서만
                              계산되고, 바깥 요소와 싸우지 않는다. */
  min-height: 78vh;     /* 100vh 는 쓰지 않는다 — 모바일 주소창 때문에 튄다 */
  display: grid; align-items: end; overflow: hidden;
}
.hero__bg{
  position: absolute; inset: 0; width: 100%; height: 100%;
  object-fit: cover;
  object-position: 50% 45%;  /* 피사체 위치에 맞춰 조정 */
  z-index: 0; pointer-events: none;
}
.hero__scrim{ position: absolute; inset: 0; z-index: 1; pointer-events: none; }
.hero__copy{  position: relative;            z-index: 2; }

절대 하지 말 것 — 이게 “글씨가 뒤로 가는” 진짜 원인입니다

  • .hero의 조상에 transform·filter·opacity:.99·will-change — 걸리는 순간 position:fixed 자식이 뷰포트가 아니라 그 조상 기준이 되고, 핀이 깨집니다.
  • 텍스트에 mix-blend-mode: difference / screen — 특정 밝기 프레임에서 글자가 통째로 사라집니다.
  • 스크림을 <video>의 filter: brightness()로 대체 — 영상 전체가 죽고, GPU 부담만 늘어납니다.
  • z-index를 9999로 올리기 — context가 다르면 아무 소용 없습니다.

지연 로딩 — 히어로 외 섹션

js// <video data-src="/media/s3.mp4" muted loop playsinline preload="none">
const io = new IntersectionObserver((entries) => {
  for (const e of entries) {
    const v = e.target;
    if (e.isIntersecting) {
      if (!v.src && v.dataset.src) v.src = v.dataset.src;
      v.play().catch(() => {});   // 자동재생 거부돼도 조용히 넘어간다
    } else {
      v.pause();                  // 화면 밖이면 정지 — 배터리·CPU 절약
    }
  }
}, { rootMargin: '200px 0px', threshold: 0.1 });

document.querySelectorAll('video[data-src]').forEach(v => io.observe(v));

스크럽 — 필요한 섹션에만

js · gsapgsap.registerPlugin(ScrollTrigger);
const video = document.querySelector('#scrubVideo');

// 메타데이터(길이)를 알아야 스크럽 범위를 계산할 수 있다
video.addEventListener('loadedmetadata', () => {
  const state = { t: 0 };
  gsap.to(state, {
    t: video.duration || 1, ease: 'none',
    scrollTrigger: {
      trigger: '#scrubSection', start: 'top top',
      end: '+=180%',        // 스크럽 구간 길이. 길수록 천천히 재생됨
      pin: true,            // ★ pin 이 없으면 영상이 위로 밀려 올라간다
      scrub: 0.6,           // 관성. 0 이면 딱딱하고, 1 이상이면 늘어진다
      anticipatePin: 1, invalidateOnRefresh: true
    },
    onUpdate: () => {
      // 재생 중이면 seek 가 무시되므로 반드시 멈춘 상태로 조작
      if (!video.paused) video.pause();
      video.currentTime = state.t;
    }
  });
});
iOS Safari에서 스크럽이 계속 끊긴다면 비디오 스크럽을 포기하고 이미지 시퀀스로 바꾸세요. canvas에 drawImage로 프레임을 그리는 방식이라 기기 편차가 없습니다. 애플이 자기 제품 페이지에서 비디오가 아니라 이미지 시퀀스를 쓰는 이유가 이것입니다.

09 / TYPE & COLOR

“안 보이거나 촌스럽거나”는
취향이 아니라 대비비 계산입니다

영상은 프레임마다 밝기가 변하므로 평균이 아니라 최악 프레임 기준으로 잡습니다. 이 페이지는 밝은 아트디렉션이라 최악 프레임이 순검정입니다 — 그래서 스크림도, 글자색도 원문 가이드와 극성이 반대입니다.

스크림 #F7F7FA를 순검정 프레임 위에 알파 a로 깔았을 때의 실제 대비비. pipeline/contrast.py로 계산 — sRGB 합성 + WCAG 상대휘도.
스크림 알파본문 잉크 #0E1116보조 잉크 #4A505A판정
0.302.14 : 11.09 : 1불합격 — 흔히 하는 실수
0.453.78 : 11.62 : 1헤드라인만 가능
0.504.51 : 11.93 : 1헤드라인 자리 채택값
0.585.88 : 12.52 : 1본문 합격
0.626.66 : 12.86 : 1본문·버튼 자리 채택값
0.7810.49 : 14.50 : 1보조 잉크가 겨우 통과
0.9014.12 : 16.06 : 1과함 — 렌더가 안 보임
원문 가이드의 표는 약간 낙관적입니다. 같은 방식으로 원문 조건(#080A0E 스크림 · 순백 프레임 · #F2F5F9 글자)을 다시 계산하면 0.58 → 4.47:1로, 원문이 적은 4.72:1이 아니라 본문 기준 4.5:1에 미달합니다. 실무 하한선은 0.58이 아니라 0.62로 잡으세요. 계산 근거는 저장소의 pipeline/contrast.py에 그대로 들어 있습니다.

여기서 나오는 설계 규칙:

  • 헤드라인이 놓이는 자리 → 알파 0.50. 대형 텍스트 3:1을 훌쩍 넘고 본문 기준도 통과합니다.
  • 본문·버튼·라벨이 놓이는 자리 → 알파 0.62 이상.
  • 보조 잉크는 영상 위에 올리지 않습니다. 알파 0.78이 필요한데, 그만큼 깔면 렌더가 죽습니다.
  • 글자가 없는 쪽은 알파 0.04까지 떨어뜨립니다. 그래서 박스가 아니라 그라디언트입니다.
  • 더 좋은 방법 — 영상 자체를 밝고 단순하게 뽑는 것. 첫 프레임 단계에서 좌우·하단을 비워두면 스크림을 얇게 깔아도 됩니다.
